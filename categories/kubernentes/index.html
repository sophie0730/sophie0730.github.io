如何監控Pod的Memory資源?

前言 最近協助專案架設監控系統，在設計kubernetes服務相關的告警時有踩到一點小坑，發現自己對於Pod的運作機制還不是那麼清楚，所以以這篇文章記錄一下。 問題簡述 在架設告警規則時，系統指標是很常見的監控來源，讓SRE能掌握系統狀況，避免服務發生故障。其中一個可能導致服務發生故障的常見原因便是OOMKilled，這個錯誤代表容器因為記憶體不足而被終止。 一種常見的OOMKilled原因是應用程式的容器memory使用量已達到他的request limit，所以其中一條告警便取用了目前container使用的memory以及這個container所設置的resource limit，使用的PromQL如下： ( sum by(pod) (container_memory_working_set_bytes{}) / sum by(pod) (kube_pod_container_resource_limits{} > 0) ) * 100 根據上述的定義，只要這個PromQL的值達到100%，容器應該就會被強致終止。當時卻觀察到許多Pods的記憶體使用量都超過100%，這個數值似乎不太合理，為什麼這些使用量超過100%的Pod不會觸發OOMKiller機制？ 如何有效觀察Pod裡面的container memory usage? 如果針對container memory usage去搜尋，會發現其實有兩種metrics可以做到： container_memory_rss container_memory_working_set_bytes
